## 1. 제품 개요 및 목표

식자재 유통 B2B 거래처가 진행 중/예정 프로모션을 한 곳에서 확인하고 직접 참여 신청할 수 있는 웹 애플리케이션. 관리자는 프로모션을 등록·관리하고 참여 현황을 확인한다. 흩어진 채널(전화, 카톡, 영업담당 개별 안내)로 인한 정보 누락을 해소하는 것이 목표다.

- 비즈니스 목표: 3,000개 이상 거래처가 프로모션 기능을 이용
- 본 문서는 3일/1인 개발 MVP 범위를 전제로 하며, 도메인 정의서(`1-domain-definition.md`)의 정의를 요구사항 수준으로 구체화한다.

## 2. 목표 사용자

- 관리자(Admin): 프로모션 등록/관리 담당자, 소수
- 거래처 담당자(Buyer): 식자재 구매 외식업체·급식업체 담당자. 목표 등록 규모 1,000개 이상 거래처

## 3. 범위

### 포함 (도메인 정의서 7절 인용)
- 관리자 프로모션 등록/수정/게시/종료
- 게임(룰렛) 적용 및 경품 목록 등록, 신청 시 즉시 추첨
- 거래처 담당자 회원가입/로그인, 프로모션 조회, 참여 신청/취소, 신청 내역 및 당첨 결과 조회
- 마이페이지(정보 수정, 비밀번호 변경)
- 모바일/데스크탑 반응형 UI

### 제외
- 실제 주문/결제/정산, 재고 실시간 연동, 승인 워크플로우, 거래처 등급별 차등가, 포인트 적립, 검색 기능, 경품 재고 관리

## 4. 기능 요구사항

### FR-1 인증
- FR-1.0 관리자 계정은 자가 회원가입 없이 DB 시드 데이터로 최초 1개 이상 생성한다
- FR-1.1 거래처 담당자는 이메일/비밀번호로 회원가입한다. 이메일 중복 시 거부한다 (EX-5)
- FR-1.2 사용자는 이메일/비밀번호로 로그인하며, 서버는 JWT access token과 refresh token을 발급한다
- FR-1.3 비로그인 사용자(유효한 access token 없음)가 보호된 기능에 접근하면 로그인 페이지로 리다이렉트한다 (EX-4)
- FR-1.4 access token 만료 시 refresh token으로 재발급받는다. refresh token도 만료/무효화된 경우 재로그인한다
- FR-1.5 사용자는 로그아웃할 수 있다. 로그아웃 시 refresh token을 무효화한다

### FR-2 프로모션 관리 (관리자)
- FR-2.1 관리자는 프로모션을 등록한다: 유형(가격할인/사은품 증정/신제품 시식), 제목, 설명, 기간(시작일/종료일), 게임 적용 여부 선택
- FR-2.2 게임 적용 프로모션은 경품 목록(이름 등)을 함께 등록한다. 경품 목록이 비어 있으면 게시할 수 없다 (EX-3)
- FR-2.3 관리자는 프로모션 내용을 수정한다
- FR-2.4 관리자는 프로모션 상태를 게시(예정→진행)/종료(진행→종료) 조작으로 수동 전환한다. 등록 시 기본 상태는 "예정"이며, 기간 경과에 따른 자동 전환은 없다 (BR-4)
- FR-2.5 관리자는 프로모션별 참여 신청 목록(신청자, 상태, 당첨 결과)을 조회한다

### FR-3 프로모션 조회 및 참여 (거래처 담당자)
- FR-3.1 거래처 담당자는 진행 중/예정 프로모션 목록과 상세를 조회한다
- FR-3.2 거래처 담당자는 프로모션에 참여 신청한다
  - 종료/미게시 프로모션은 신청 불가 (BR-3, EX-2)
  - 이미 신청한 프로모션 재신청 시도는 거부, 기존 신청 존재를 안내한다 (BR-1, EX-1)
  - 게임 적용 프로모션은 신청 즉시 서버가 경품 중 하나를 무작위 추첨해 결과를 확정하고, 화면은 룰렛 애니메이션 후 결과를 표시한다 (BR-2)
- FR-3.3 거래처 담당자는 신청을 취소한다. 취소는 기존 신청 레코드의 상태 전환으로 처리하며 재신청 시 새 레코드를 만들지 않는다 (BR-1). 재신청 시에는 새로운 신청 행위이므로 게임 적용 프로모션은 다시 추첨한다 (BR-2)
- FR-3.4 거래처 담당자는 내 신청 목록과 당첨 결과를 확인한다

### FR-4 마이페이지 (공통)
- FR-4.1 사용자는 내 정보를 조회/수정한다
- FR-4.2 사용자는 비밀번호를 변경한다

## 5. 비기능 요구사항

- 성능/확장성: 등록 거래처 1,000개 이상, 프로모션 이용 거래처 3,000개 이상 규모를 목표로 하되, MVP는 단일 서버/단일 DB 인스턴스 기준으로 별도 캐싱·부하분산 없이 처리 가능한 수준으로 구현한다. 별도 성능 튜닝은 MVP 범위 밖.
- UI: 반응형 웹 UI 필수 적용(모바일/데스크탑 대응). 별도 모바일 앱 없음
- 접근성: 본 프로젝트에서는 고려하지 않음
- 보안: 비밀번호는 해시 저장. 인증은 JWT 기반으로 access token(단기, API 요청 인가)과 refresh token(장기, access token 재발급용)을 함께 사용한다. refresh token은 재발급 시 로테이션한다
- 데이터 정합성: 참여신청 유일성(BR-1)은 DB 유니크 제약(promotion_id, buyer_id)으로 보장

## 6. 기술 스택 및 아키텍처 제약

- 프론트엔드: React 19, 전역상태관리 Zustand, 서버 상태/통신 TanStack Query
- 백엔드: Node.js + Express, pg 라이브러리로 PostgreSQL 직접 접근 (별도 ORM 도입 없음)
- 데이터베이스: PostgreSQL 17
- 배포/인프라: 별도 요구사항 없음, MVP 로컬/단일 환경 기준

## 7. 일정 및 마일스톤 (3일)

- Day 1: DB 스키마 설계 및 마이그레이션, 인증(회원가입/로그인), 프로모션 CRUD API 및 관리자 화면
- Day 2: 거래처 담당자 프로모션 조회/참여 신청/취소 API 및 화면, 룰렛 추첨 로직, 참여 현황 조회(관리자)
- Day 3: 마이페이지, 반응형 UI 마무리, 예외 케이스(EX-1~5) 처리 점검, 통합 테스트 및 버그 수정

## 8. 리스크 및 가정

- 리스크: 1인/3일 개발로 테스트 커버리지가 제한적임 → 핵심 비즈니스 규칙(BR-1~4)과 예외 케이스(EX-1~5) 위주로 검증
- 리스크: 동시 다발 참여 신청 시 유니크 제약 위반 처리(EX-1)를 API 레벨에서 명확히 에러 응답으로 처리해야 함
- 가정: 사용자 수 목표(1,000/3,000)는 MVP 검증 이후 목표치이며, MVP 자체는 소규모 트래픽 기준으로 개발함
- 가정: 결제/정산/재고 등 외부 시스템 연동 없음 (MVP 제외 범위와 동일)
