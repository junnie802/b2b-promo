## 시나리오 1. 회원가입

- 정상 가입 → `201`, `s1-01-signup.json`
- EX-5(이메일 중복) → `400 {"error":"이미 등록된 이메일입니다"}`

### ⚠️ 테스트 진행 중 발견: curl 명령줄 인자로 한글을 직접 전달하면 인코딩이 깨짐

`curl -d '{"name":"박바이어",...}'` 형태로 한글을 셸 인자에 직접 넣으면 Windows/git-bash 환경에서 코드페이지 변환이 발생해 실제로 운영 DB에 깨진 문자열(`�ڹ��̾�` 등)이 저장됨을 확인했습니다. 손상된 테스트 레코드는 즉시 삭제했고, 이후 모든 요청은 UTF-8로 저장한 JSON 파일을 `--data-binary @file`로 전송하는 방식으로 전환해 정상 처리를 확인했습니다.
- **이건 애플리케이션(백엔드) 버그가 아니라 테스트 도구(curl 셸 인자) 이슈**입니다. 실제 서비스는 브라우저 `fetch`/`axios`로 UTF-8 JSON을 그대로 전송하므로 영향 없습니다.
- 다만 백엔드가 요청 인코딩을 검증하지 않고 그대로 저장한다는 점은 참고할 부분입니다.

## 시나리오 2. 로그인/로그아웃/토큰

- buyer/admin 로그인 → `200`, 토큰 발급 (`s2-01`, `s2-02`)
- EX-4(토큰 없이 보호 API 접근) → `401 {"error":"인증 토큰이 필요합니다"}`
- 토큰 재발급 (`/api/auth/refresh`) → `200`, refresh token 로테이션 확인(`s2-03`)
- 로그아웃 → `204` (`s2-04`)
- 로그아웃된 refresh_token으로 재발급 시도 → `401 {"error":"유효하지 않거나 만료된 refresh token입니다"}` (`s2-05`, FR-1.5 정상)
- 권한 불일치(buyer가 관리자 전용 API 호출) → 시나리오 7에서 `403` 확인

## 시나리오 3. 관리자 프로모션 등록~게시

- 등록 시 상태 "scheduled" 생성 → 게시 → "active" 전환 확인 (`s3-01`, `s3-02`)
- EX-3(경품 0건 게시 시도) → `400 {"error":"경품이 없어 게시할 수 없습니다"}` (`s3-04`)
- 경품 2건 추가 후 게시 → 성공 (`s3-05`, `s3-06`)
- EX-2 테스트용 예정(id=3)/종료(id=4) 프로모션 준비 (`s3-07`~`s3-10`)

## 시나리오 4. 거래처 프로모션 조회/신청

- 목록 조회(`status=active`) → 정상 2건 반환 (`s4-01`)
- 참여 신청 → `201`, `status:"applied"` (`s4-02`)
- EX-1(중복 신청) → `400 {"error":"이미 참여 신청한 프로모션입니다"}` (`s4-03`)
- EX-2(예정 프로모션 신청) → `400 {"error":"게시 중인 프로모션에만 참여 신청할 수 있습니다"}` (`s4-04`)
- EX-2(종료 프로모션 신청) → 동일 메시지로 거부 (`s4-05`)

### 참고사항: `status=ended`로 조회 시 필터가 무시됨

buyer 토큰으로 `GET /api/promotions?status=ended` 호출 시 종료된 프로모션(id=4)은 노출되지 않아 **보안/데이터 유출 문제는 없으나**, 빈 배열이 아니라 scheduled+active 전체 목록이 반환됩니다(`ended` 값이 허용되지 않아 필터 자체가 무시되는 것으로 보임). FR-3.1의 "ended는 조회되지 않는다"는 조건은 충족하지만, 클라이언트가 "종료" 탭에서 이 응답을 그대로 쓰면 예정/진행 항목이 잘못 표시될 수 있어 참고로 남깁니다.

## 시나리오 5. 게임 적용 프로모션 참여 (룰렛 추첨)

- 신청 시 즉시 추첨되어 응답에 `prize_id`/`prize_name`("보온병") 포함 (`s5-01`)
- BR-2: `/api/applications/me` 재조회 시 동일 결과 유지 확인 (`s5-02`)

## 시나리오 6. 신청 취소/재신청

- 취소 → `status:"cancelled"` (`s6-01`)
- 재신청(게임 미적용) → 동일 레코드 id 재사용, `status:"applied"`로 복귀 (BR-1, `s6-02`)
- 게임 적용 프로모션 취소 후 재신청 → 재추첨되어 결과가 "보온병" → "텀블러"로 갱신 (BR-2, `s6-03`, `s6-04`)

## 시나리오 7. 관리자 참여 현황 조회

- 신청 1건 있는 프로모션(id=2) 조회 → 신청자/거래처/상태/당첨경품 정상 반환 (`s7-01`)
- 신청 0건 프로모션(id=4) 조회 → 빈 배열 `[]` (`s7-02`)
- buyer 토큰으로 조회 시도 → `403 {"error":"권한이 없습니다"}` (`s7-03`)

## 시나리오 8. 마이페이지

- 내 정보 조회 → `password_hash` 미포함 확인 (`s8-01`)
- 정보 수정(거래처명) → 반영 확인 (`s8-02`)
- 비밀번호 변경(현재 비밀번호 오류) → `400 {"error":"현재 비밀번호가 일치하지 않습니다"}` (`s8-03`)
- 비밀번호 변경(정상) → `204` (`s8-04`)
- 새 비밀번호로 재로그인 → `200` 성공 (`s8-05`)

## 종합 결론

- 운영 배포 백엔드(Vercel + Supabase)에서도 로컬 환경과 동일하게 BR-1~4, EX-1~5가 모두 정상적으로 강제됨을 확인
- 인증(로그인/로그아웃/토큰 재발급/로테이션) 플로우가 운영 환경에서도 정상 동작
- 프론트엔드(`abc-7782-fe.vercel.app`)는 현재 404로 응답해 미배포 또는 배포 오류 상태로 보이며, 브라우저 기반 시나리오 테스트는 프론트 배포 후 별도로 수행이 필요함
- curl 명령줄 인자의 한글 인코딩 이슈(테스트 방법론 문제, 애플리케이션 버그 아님)로 손상된 테스트 레코드 1건은 즉시 삭제 후 재검증함
